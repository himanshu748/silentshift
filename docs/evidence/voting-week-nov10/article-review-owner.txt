					137 text Versioning and idempotency solve different problems.  expected_version  prevents a new decision based on stale evidence. The idempotency key identifies a decision that may already have committed.
				138 text The distinction becomes visible after a failure. Saving the first decision advances the case version. Native workflow events can advance it again. A retry of the same decision still carries its original version; replacing that version would change the request the operator authorized.
				139 text The implementation checks for the receipt before applying the new-decision version check. Its control flow can be summarized as follows; this is explanatory pseudocode:

				144 text The fingerprint includes the authenticated reviewer and canonical request body. Reusing the same key with a different reason, action or version is a conflict. Choosing a new key also cannot replace an already committed task decision. These checks give a retry a narrow meaning: continue the recorded decision.

					154 text Before completing a task, the server verifies the task/case binding, reviewer assignment and matching committed receipt. For approval, it re-evaluates policy. The task's  OnAction  callback uses that same authorization boundary, so invoking a native Workflow action directly cannot bypass the application decision.
				155 text There is another failure window inside native completion: the worklist item can be removed before its deferred response is successfully enqueued. Recovery cannot rely exclusively on finding that item again. The completion code checks the persisted task and receipt, then resumes through the guarded task callback when needed. The pending-task API also includes receipt-backed held cases so this intermediate state remains discoverable.
				156 text At the final boundary, the simulator destination independently checks policy and persists a unique receipt. The concurrency test sent two simultaneous identical approvals. Both requests returned HTTP 200; the observed result was one review receipt, one native completion response and one delivery.
				157 text That is the demonstrated guarantee for this persisted simulator. A real shipment or payment endpoint would need its own effect and retry contract; these tests do not establish exactly-once behavior for arbitrary external systems.
